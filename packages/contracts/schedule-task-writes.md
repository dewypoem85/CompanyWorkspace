# 일정 업무 저장의 공통 응답 계약

## 범위와 호환성

`TaskWriteProtocol`은 기존 `POST /api/tasks`, `PUT /api/tasks/{id}`, `PATCH /api/tasks/{id}/status`에 공통 `workspace-form-v1` 응답을 선택적으로 제공하는 서버 어댑터다. 본문은 `TaskInput`/`StatusInput` JSON을 유지한다. 업무 날짜는 시작일·종료일만 포함하며 제거된 실제 시작일·실제 종료일 필드는 받거나 반환하지 않는다. 기존 URL·서비스 배포 경계는 변경하지 않는다. 공통 폼의 현재 native POST/FormData 전송을 JSON PUT/PATCH로 위장하지 않는다.

TaskPanel의 생성·수정·상태 변경은 `useTaskWrites`에서, 칸반의 상태 선택·드래그 변경은 `useTaskQuickStatus`에서 generated 공통 JSON 전송·확인창·문서 작업 세션에 연결한다. 도메인의 `taskWrites`가 전체 ACK를 검증하며 정상 확인 전에는 입력과 기준을 비우거나 칸반 행을 이동하지 않는다. 댓글·보관/복원은 이번 쓰기 계약 범위가 아니며 이미지 임시 업로드는 별도 `schedule-image-uploads.md`를 따른다.

칸반 빠른 상태 변경은 화면에 표시된 업무 ID·버전·현재 상태를 먼저 고정하고, 전송 전에 현재 계정과 상세 GET을 다시 확인한다. 새 상세가 화면 행과 정확히 일치할 때만 확인창을 열며 확인 중 행·필터·계정이 바뀌면 취소한다. 처리 중에는 해당 상태 선택과 모든 드래그를 잠그고, 검증된 전체 ACK 뒤에만 보드를 다시 조회해 행을 이동한다. ACK는 저장됐지만 후속 보드 조회만 실패한 경우 PATCH를 반복하지 않고 읽기만 다시 시도할 수 있게 한다. 범위 변경·pagehide·timeout처럼 결과를 확정하지 못한 전송은 같은 문서 세션을 잠근다.

## 요청과 조회 기준값

- `Accept: application/vnd.company.workspace-form+json`을 명시하면 공통 응답을 받는다. 파라미터와 복수 Accept를 허용하되 해당 타입의 `q=0`은 선택하지 않는다. 기존 JSON 또는 wildcard만 보내는 클라이언트는 기존 업무 객체/오류 형식을 유지한다.
- `X-Workspace-Actor`는 작성 당시 회사 사용자 ID의 정규 십진 문자열이다. 현재 인증된 `Access.Me()`의 ID와 정확하게 일치해야 한다. 인증 수단이 아니며 세션·중앙 계정 확인·CSRF·업무/담당자/프로젝트 인가는 계속 서버에서 수행한다.
- 상세 GET은 기존 task/comments/attachments/history/canEdit에 `editing: { actorId, stateToken }`을 추가한다. 이전 클라이언트의 필드는 유지한다. GET 스냅샷은 쓰기 승인 자체가 아니다.
- 기존 업무 PUT/PATCH는 `X-Workspace-State`와 기존 `Version`을 모두 제출한다. 신규 POST는 Version=0이며 state 헤더를 보내지 않는다.
- stateToken은 업무의 모든 저장 필드와 **본문 첨부**의 모든 메타데이터를 포함하는 SHA-256이다. 업무 ID, 제목/원문, 담당자/작성자/프로젝트, 시작일·종료일, 상태/보관/버전/시각 및 첨부 ID·소유자·연결·이름·유형·크기·시각을 대조한다. 첨부 정렬과 SQLite DateTime.Kind 왕복 차이에 독립적이다.
- 댓글/댓글 첨부·이력 추가는 업무 본문 변경이 아니므로 기준값에 넣지 않는다. 업무 수정으로 댓글을 덮어쓰지 않는다. 원문 속 JSON/큰 정수는 문자열로 보존한다.

## 저장 응답

HTTP 200과 위 media type으로 다음 envelope를 반환한다.

```text
protocol: workspace-form-v1
outcome: saved
message: 사용자 안내
data:
  operation: create | update | status
  actorId: 정규 십진 문자열
  previousStateToken: 제출 전 전체 기준값 (신규는 null)
  stateToken: 저장된 전체 기준값
  task: 실제 저장된 WorkItem 전체
  attachments: 실제 저장된 본문 첨부 전체 (댓글 첨부 제외)
  navigateTo: /tasks/{정확한 저장 업무 ID}
```

소비자는 HTTP 200만으로 초안을 비우지 않는다. 현재 작업/계정·operation·ID·이전/새 기준값·전체 task와 첨부·이동 경로를 검증하고 제출 의도 및 이전 스냅샷과 대조해야 한다. 제목/본문은 기존 trim, 첨부 ID는 기존 중복 제거 정책을 유지한다. 상태 변경은 나머지 필드를 유지한다.

## 트랜잭션과 실패

- PUT/PATCH는 트랜잭션을 시작한 뒤 업무/인가·Version·전체 기준값을 읽고 비교한다. SQLite 쓰기 트랜잭션과 기존 EF Version 동시성 검사를 유지해 두 요청이 같은 기준으로 동시에 성공하지 않도록 한다.
- 생성·수정·상태 변경은 기존 업무·첨부·감사/알림 DB 반영 후 같은 트랜잭션 안에서 실제 결과를 읽고 JSON 값으로 고정한다. `CommitAsync` 성공 뒤에만 결과를 반환한다. 저장 후 별도 GET의 더 늦은 값을 해당 쓰기의 ACK로 바꾸지 않는다.
- 첫 DB 쓰기 **이전**의 입력 거부는 422/invalid, 기준 충돌은 409/conflict, 권한 거부는 401/403/denied다. 없는/숨겨진 업무의 404는 원래 상태를 유지하고 unknown으로 표시한다. 중앙 인증/CSRF 미들웨어와 JSON 바인딩은 앞단에서 기존 오류 형식을 반환할 수 있다. 이 응답도 성공으로 해석하면 안 된다.
- 첫 쓰기 이후의 예외는 500/unknown이다. 내부 오류 내용은 응답에 넣지 않는다. 실제 트랜잭션이 롤백된 경우도 있지만 클라이언트에 이를 확약하거나 재전송을 권하지 않는다. 커밋 직후 관찰/응답 오류라면 실제 DB에는 저장되어 있을 수 있다.
- 신규 업무는 ID 배정을 위한 첫 SaveChanges 뒤 첨부를 연결한다. 따라서 첨부 연결에서 거부되면 실제 SQLite 트랜잭션이 롤백되더라도 보수적으로 unknown이다. 기존 업무의 첨부 검증은 첫 쓰기 전이므로 잘못된 첨부를 invalid로 교정할 수 있다.
- 문서/브라우저 취소는 서버 롤백이 아니다. 결과 미확정에는 내역 확인만 제공하고 공통 문서 세션이 반복 쓰기를 잠근다. 이 계약 자체에는 생성 요청의 영구 멱등성·다른 탭 중복 생성 방지·다른 서비스 DB 통합이 없다.

## 실제 편집 화면 수명주기

- 생성/수정/상태마다 입력·기존 본문 첨부·현재 계정을 복사한 뒤 문서 세션 lease를 얻는다. fresh 회사 정보와 전체 상세 GET을 공통 읽기 세션으로 확인한다. 필드가 변경되거나 기준값이 다르면 전송하지 않는다.
- 공통 확인창에는 제목·담당자(회사 프로필)·한국어 상태·첨부 수를 표시한다. 확인 도중 폴링을 멈추지 않으며 최신 상세가 바뀌면 기존 의도로 실행하지 않는다. 전송과 저장 후 조회 동안에만 관련 편집을 잠근다.
- 신규 업무를 프로젝트 미지정으로 등록하거나 기존의 지정 프로젝트를 미지정으로 제거할 때는 일반 저장 확인 전에 별도의 `프로젝트를 지정하지 않고 저장할까요?` 확인을 거친다. 취소하면 초안과 선택값을 그대로 유지하며 전송하지 않는다. 이미 미지정인 업무의 다른 필드 수정과 상태 변경에는 경고를 반복하지 않는다.
- JSON 전송은 `CompanyForm.createTransport` 하나가 소유한다. same-origin/CSRF/계정·기준값 헤더를 유지한다. 전체 응답은 전송한 JSON·업무/모든 수정 필드·불변 메타데이터·전체 첨부와 대조한다. SQLite의 UTC suffix 차이는 허용하지만 시간이 뒤로 가는 응답은 거부한다. 기준 해시는 서버의 불투명 값이며 JS에서 별도 해시를 추정하지 않는다.
- 검증된 ACK 후에만 저장값/새 기준을 반영한다. 후속 상세·목록 GET의 실패는 저장 성공과 별개이며 `저장 결과 다시 조회`로 GET만 재실행한다. 신규 업무 이동도 정확한 저장 ID와 후속 읽기를 확인한 뒤 수행한다. 댓글 초안은 상태 변경으로 지우지 않는다.
- 정확한 422 invalid는 수정 후 다시 시도할 수 있다. 정확한 409 conflict는 사용한 이전 기준만 소모한다. 본문 편집은 명시적인 3방향 비교로 새 기준을 선택하고, 상태 변경은 현재 업무를 다시 읽은 뒤 사용자가 새 상태를 선택한다. 자동 덮어쓰기/재전송은 하지 않는다.
- HTML/잘못된 ACK/네트워크/timeout/전송 후 계정 변경은 unknown으로 취급한다. 같은 SPA 문서에서 편집기를 닫았다 다시 열어도 `documentSession('schedule-task-writes')`의 잠금은 유지된다. 다른 탭에서 내역을 확인하도록 안내한다.
- 전송하기 전의 계정 범위 변경만 원래 소유자의 명시적인 회사/상세 재검증 뒤 복구할 수 있다. 본문 비교와 기존 보관 작업의 명시적 재확인 모두 검증된 상세/디렉터리를 같은 recover 경로에 전달한다. 자동 폴링 성공으로 잠금을 해제하지 않는다. 모든 실제 전송 직전에 `lease.markSent()`를 호출한다. 전송 중 변경·unknown·실제 pagehide는 GET으로 복구하지 않는다. 늦은 응답/해제는 입력·기준·후속 조회를 반영하지 않는다.

## 검증

`TaskWriteProtocolTests`는 실제 TestServer/임시 SQLite·합성 SSO/디렉터리와 업로드를 사용한다. 생성/수정/상태 전체 ACK·본문/첨부/댓글 보존, 레거시/Accept 호환, 모든 fingerprint 필드·정렬/시각, 계정/권한/CSRF/비공개/보관, 잘못된/다른 업무/첨부만 바뀐 기준값, 동시 쓰기, DB 오류와 커밋 **직전/직후** 예외를 검사한다. 커밋 이후 오류에서는 DB에 실제 업무/감사가 남아 있음을 단언한다.

`check-schedule-task-writes.mjs`와 변이 테스트는 서버 계약과 TaskPanel·칸반 실제 UI의 공통 전송/확인/문서 세션·전체 ACK 연결 누락 및 App의 raw 상태 PATCH 재도입을 탐지한다. 완전한 정적 의미 분석이나 실제 서버 테스트의 대체재가 아니다. 페이지 생성기 격리 검사에도 동일 검사와 소스를 포함한다.

`taskWrites.test.ts`는 전체 필드/첨부/입력/ID 대조, `useTaskWrites.test.ts`와 `useTaskQuickStatus.test.ts`는 실제 공통 런타임과 React를 연결해 후속 GET 실패·늦은 ACK·계정/라우트/해제·확인 중 변경·오래된 칸반 행·잘못된 ACK 잠금을 검사한다. `schedule-shell.spec.mjs`는 합성 HTTP와 실제 번들/Chrome으로 신규/수정/상태, 칸반 확인 취소·저장 후 행 이동, 초안·충돌·프로필·PC/모바일·두 테마를 검사한다. 합성 브라우저 기준 해시는 서버 해시 알고리즘의 증명이 아니며 실제 서버의 hash/DB 왕복은 `TaskWriteProtocolTests`가 담당한다. 운영 SSO/DB/배포 검증은 별도다.
