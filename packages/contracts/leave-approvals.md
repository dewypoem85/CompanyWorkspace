# 연차 승인 화면 계약

대상은 Leave `/Admin` 및 `/Admin/Index`의 일반 승인/반려, 취소 승인/반려, 강제 삭제다. 연차 신청·달력·발생 보정·정산 화면까지 전환된 것은 아니다.

## 공통 폼과 업무 경계

`_ApprovalAction.cshtml`이 세 handler의 native POST/antiforgery/대상·기준값 필드를 함께 렌더링한다. `approval-forms.js`는 확인한 업무 대상과 입력을 보존하며 `CompanyForm`, `CompanyDialog`, `CompanyState`를 사용한다. 실행 확인은 직원·날짜·신청 번호와 강제 삭제 사유를 표시한다. 동기식 별도 실행 confirm과 기존 인라인 폴링 코드는 제거했다.

서버 handler는 기존 AdminOnly/중앙 세션, 서비스의 자기 신청 처리 금지, 강제 삭제 권한·사유 정책을 유지한다. `LeaveRequestService`의 상태 전환·가불 정산·배정 삭제·감사·알림은 변경하지 않는다. 회사 마스터의 신청은 목록과 새 처리 경로에서 제외한다. 화면 숨김은 서버 인가를 대체하지 않는다.

## 요청과 확인 응답

- `id`: 신청 ID. 폼과 응답은 문자열을 사용하며 JavaScript Number로 변환하지 않는다.
- `expectedEmployeeId`: 화면을 연 **Leave 로컬 직원** ID. Portal CompanyUserId와 혼용하지 않는다. 현재 서버 직원과 정확히 대조한다.
- `expectedSnapshot`: 신청 ID/직원/상태/관련 시각·처리자·사유/인수인계·일수/가불값/날짜 목록의 SHA-256. 화면 당시 값과 현재 DB 값을 대조한다. 클라이언트 서명이나 비밀 토큰이 아니며 인가를 대신하지 않는다.
- `approve`: 일반/취소 결정의 정확한 `true`/`false`. 클릭한 submitter를 공통 폼이 전송한다. 강제 삭제에는 `reason`이 필요하다.

enhanced 폼은 공통 media type과 `workspace-form-v1`을 사용한다. `saved.data`는 `{operation, employeeId, id, approve, previousSnapshot, status}`이며 `approve`는 문자열 또는 강제 삭제 시 null, 나머지는 문자열이다. 성공 상태는 `Approved`/`Rejected`/`Cancelled`/`deleted`다. 클라이언트는 전체 응답과 제출 대상/행동/원래 스냅샷 및 현재 입력의 일치를 확인한 다음 해당 신청의 반복 처리를 잠근다.

검증 가능한 입력 문제는 422, 다른 직원/스냅샷/이미 처리된 상태/없는 대상은 409, 권한은 403이다. 예전 native 폼의 기준값 없는 요청은 호환되지만 enhanced 요청에는 두 기준값이 필수이며, native에도 하나라도 있으면 모두 대조한다. native 성공은 기존 redirect, 실패는 새 목록과 오류 및 HTML 인코딩한 제출 삭제 사유를 표시하고 반복 제출을 잠근다. 새 화면을 열기 전 현재 값으로 재기준화하여 재전송하지 않는다.

## 저장·조회·초안 수명주기

한 화면에서 실행 확인/쓰기는 한 번에 하나만 진행한다. 다른 신청의 삭제 사유가 있으면 저장 성공 후 자동 목록 교체를 보류하며, 해당 사유를 유지한다. 전체 응답이 확인된 신청만 처리 버튼을 잠근다. 새로고침/최근 목록 이동으로 사유를 버릴 때는 별도 공통 확인이 필요하다. 조회는 POST를 재실행하지 않는다.

자동 대기열 감시는 기존 3초 주기를 유지하지만 편집/확인/쓰기/미확정 결과 동안 목록을 교체하지 않는다. `CompanyReadSession`의 `approval-summary`와 `approval-lists` 채널이 15초 관찰 제한, 취소와 최신 요청 판정을 맡는다. 배경 summary 요청은 사용자의 처리 확인이 시작되면 중단하고 늦은 결과를 배제한다. 명시적 목록 조회는 두 영역을 함께 검증한 뒤 교체하며 선택한 최근 목록 쿼리를 유지한다. summary의 감사 로그 version은 문자열이고 기존 안전한 숫자만 호환 수신한다.

확인된 처리와 후속 목록 갱신 실패는 구분한다. 실패/미확정에는 초안을 보존하고 자동 재전송하지 않으며, 명시적 최신 조회 후에만 다시 처리할 수 있다. 조회 실패를 빈 대기열이나 자동 로그인 이동으로 바꾸지 않는다. 계정 범위 변경/조회 권한 거부는 이전 신청 영역과 확인창을 숨기고 새 문서 확인을 요구한다. 비지속 pagehide에서 폼·확인창·폴링/조회·리스너를 해제하고 늦은 응답을 적용하지 않는다.

## 보장하지 않는 것

스냅샷은 handler의 읽기 시점 비교다. 현재 DB 모델에 새 concurrency token/원자적 상태 전환/멱등성 키를 추가하지 않았으므로 읽기와 서비스 쓰기 사이의 경쟁을 해결한 것은 아니다. 기존 서비스는 업무 저장, 감사, 알림을 별도 단계로 실행한다. 뒤 단계의 예외가 이미 반영된 신청을 롤백했다고 단정할 수 없어, 내부 예외를 로그에만 남기고 500 미확정으로 안내한다. 실제 통합 테스트에서 신청 변경 후 감사 실패를 재현한다. 자동 재시도나 운영 기록 수정으로 이를 복구하지 않는다.

현재 문서의 초안만 보존하며 브라우저 저장소·다른 탭에 복제하지 않는다. 새 탭에서 같은 신청을 동시에 실행하는 경쟁 제어, 실제 Discord 수신 보장, 운영 배포까지 증명하는 계약은 아니다.
