# PlayFab 플레이어 데이터 조회·편집

## 범위

CS 화면 `/player-data.html`은 PlayFab API로 플레이어 데이터 저장소의 키와 값을 조회하고 편집합니다.

| 화면 저장소 | 조회 API | 저장 API | 비고 |
| --- | --- | --- | --- |
| 플레이어 데이터 | `Server/GetUserData` | `Server/UpdateUserData` | 저장 Permission `Private`, SaveData 압축 지원 |
| 읽기 전용 데이터 | `Server/GetUserReadOnlyData` | `Server/UpdateUserReadOnlyData` | 클라이언트에서 읽기만 가능한 운영 데이터 |
| 내부 데이터 | `Admin/GetUserInternalData` | `Server/UpdateUserInternalData` | 클라이언트에 노출되지 않는 서버 전용 데이터 |

UID 조회 한 번으로 세 저장소 API를 병렬 호출하며 `Keys` 필터를 보내지 않아 현재 설정된 키를 모두 불러옵니다. 화면은 플레이어 데이터, 읽기 전용 데이터, 내부 데이터 순서로 영역을 나누고 각 영역에 키, 값 미리보기, 형식, 크기, 변경 시각을 표시합니다. 전체 검색, 저장소별 신규 키 추가, 상세 편집, 삭제를 지원합니다. 상세 편집기는 선택한 행 바로 아래에 펼쳐지고 한 번에 하나만 열리며, 같은 행을 다시 선택하면 접힙니다. JSON은 상세 편집기에서 자동으로 들여쓰기하되 숫자와 문자열 토큰 원문은 보존합니다. 일반 문자열은 그대로 표시·편집합니다.

각 저장소는 별도의 DataVersion, 편집 토큰, 원본 스냅샷을 유지합니다. 따라서 한 화면에 함께 표시하더라도 추가·수정·삭제의 동시 변경 검증은 실제 PlayFab 저장소 경계를 넘지 않습니다.

상세 행은 공통 `CompanyDisclosure`의 단일 펼치기 모드를 사용합니다. 대용량 편집기는 하나만 생성하며 선택한 행 아래로 이동합니다. 접기 또는 검색으로 숨겨도 작성 중인 값·처리 사유·확인 체크·커서·편집기 스크롤은 유지합니다. 같은 키를 다시 열면 초안을 이어서 편집할 수 있고, 다른 키/서버로 전환할 때는 변경사항 폐기 확인을 받습니다. 초안은 열린 페이지 안에만 보존하며 브라우저 저장소에 영구 저장하지 않습니다.

조회·저장 요청 중에는 대상 서버/UID, 검색, 편집 및 추가·삭제 입력을 잠가 요청 대상이 바뀌거나 중복 제출되지 않도록 합니다. 조회 실패나 저장 충돌은 기존 편집 초안을 유지합니다. 모바일에서는 표의 가로 스크롤과 상세 편집기의 너비를 분리하여 상세 입력이 화면 폭 안에서 동작합니다.

저장 확인은 공통 확인창, 추가·삭제는 공통 모달 프레임과 도메인 입력 폼을 사용합니다. 취소 시 실행하지 않으며 저장 응답의 대상·내용·새 토큰을 확인한 뒤에만 편집 기준을 갱신합니다. 통신 끊김·HTML·불완전 응답은 서버 반영 여부 미확정으로 안내하고 초안을 유지합니다. 충돌/미확정 결과 뒤에는 최신 조회 전까지 같은 편집 토큰으로 반복 실행하지 않습니다. 45초 통신 제한은 서버 처리 취소나 롤백을 뜻하지 않습니다.

추가·삭제가 완료된 뒤 목록 조회만 실패하면 완료 사실을 유지하고 **목록 다시 확인** 버튼을 표시합니다. 이 버튼은 읽기만 수행하며 같은 추가·삭제를 반복하지 않습니다. 그 사이 새 초안을 작성했다면 조회 적용 전에 폐기 확인을 받습니다. 로그인·권한 범위가 변경되면 열린 창을 닫고 이전 범위의 지연 응답은 적용하지 않습니다. 새 조회 전까지 쓰기를 막으며 초안은 화면 안에 유지합니다. 실제 서버 권한 검증과 감사 기록은 기존대로 수행합니다.

상세 편집기는 조회 당시 원본과 현재 값을 줄 단위로 실시간 비교합니다. 수정된 줄은 주황색, 새로 추가된 줄은 초록색 배경으로 표시하고 삭제된 줄은 상단의 빨간 요약 배지와 삭제 지점의 빨간 선으로 표시합니다. 이전·다음 버튼 또는 `Alt+↑`·`Alt+↓`로 연속된 변경 블록을 순회할 수 있으며, 선택한 블록은 편집기 중앙으로 이동하고 테두리로 강조됩니다. 편집기 스크롤과 강조 레이어는 함께 이동하며, 원본 복원 또는 저장 후 다시 조회하면 강조 표시가 초기화됩니다.

## SaveData 압축

압축 처리는 플레이어 데이터(`UserData`) 저장소의 `SaveData-Compression` 키에만 적용합니다. 형식은 다음과 같습니다.

```text
gzip-v1:<원본 UTF-8 바이트 수>:<표준 Base64 GZip 데이터>
```

서버는 원본 크기, 표준 Base64, GZip CRC32, 최대 32MB, 엄격한 UTF-8을 확인한 뒤 원문을 표시합니다. 압축 키가 없거나 손상됐고 기존 `SaveData`가 있으면 그 값을 폴백으로 표시합니다.

`SaveData` 또는 `SaveData-Compression`을 수정 저장하면 편집 원문을 BOM 없는 UTF-8로 변환하고 GZip + 표준 Base64로 압축해 `SaveData-Compression`을 갱신합니다. 같은 요청에서 기존 `SaveData` 키는 제거합니다.

ES3 JSON의 64비트 정수를 보호하기 위해 서버와 브라우저는 `JSON.parse()` 결과를 다시 `JSON.stringify()`해 저장하지 않습니다. JSON 구문을 검사한 뒤 토큰 기반 lossless 포매터가 가독성을 위한 공백과 들여쓰기만 바꾸며, 숫자 리터럴과 문자열 이스케이프는 그대로 보존합니다.

## 환경변수

라이브/테스트 Title ID와 Secret Key는 상품 지급·회수 기능과 공통으로 사용합니다. 두 환경이 모두 설정되어 있으면 화면의 기본 선택은 라이브 서버이며, 라이브 설정이 없을 때만 테스트 서버로 대체합니다.

```dotenv
PLAYFAB_LIVE_TITLE_ID=
PLAYFAB_LIVE_SECRET_KEY=
PLAYFAB_TEST_TITLE_ID=
PLAYFAB_TEST_SECRET_KEY=

PLAYFAB_PLAYER_DATA_MOCK_MODE=false
PLAYFAB_PLAYER_DATA_LIVE_ENABLED=false
PLAYFAB_PLAYER_DATA_TEST_ENABLED=false
```

Title ID와 Secret Key가 설정된 서버는 조회할 수 있습니다. 실제 저장은 해당 서버의 `PLAYFAB_PLAYER_DATA_*_ENABLED=true`일 때만 가능합니다. 상품 지급·회수 쓰기 플래그와는 독립적입니다.

## 저장 안전장치

1. 조회 시 서버가 저장소까지 묶인 15분 유효 편집 토큰과 대상 키의 SHA-256 스냅샷을 보관합니다.
2. 브라우저와 서버 모두 최대 크기를 검사하며 세이브 키는 JSON 구문도 검증합니다.
3. 담당자는 처리 사유를 입력하고 대상·변경 내용을 최종 확인해야 합니다.
4. 수정·삭제 직전에 선택한 키를 PlayFab에서 다시 조회합니다. 세이브 저장은 `SaveData`와 `SaveData-Compression`을 함께 재검증합니다.
5. 조회 당시 원본 저장값과 현재 값의 존재 여부 또는 해시가 다르면 HTTP 409로 중단합니다.
6. 신규 키는 저장 직전 같은 키가 없는지 다시 확인하며, 중복 키를 덮어쓰지 않습니다.
7. 일반 키는 선택한 키 하나만 갱신·삭제합니다. 세이브 수정은 `SaveData-Compression`을 갱신하고 레거시 `SaveData`를 제거한 뒤 최신 데이터를 다시 조회합니다.

PlayFab `UpdateUserData`는 조건부 쓰기 API가 아니므로 재조회와 실제 쓰기 사이의 매우 짧은 경쟁 구간 자체를 없애지는 못합니다. 같은 CS 인스턴스 안의 동일 UID·키 저장은 잠금으로 직렬화합니다.

## 감사 로그

`/app/data/player-data-audit.jsonl`에 추가·수정·삭제 시도와 결과를 기록합니다.

- Company Portal 직원 ID, 이름, 이메일
- 요청 ID, 서버 환경, 데이터 저장소, PlayFab UID, 키, 처리 사유
- 변경 전후 바이트 수와 SHA-256 해시
- 조회/현재/저장 후 DataVersion
- 성공, 실패 상태

세이브 JSON 원문은 기록하지 않습니다. 저장 시도 감사 로그를 먼저 쓸 수 없는 경우 실제 PlayFab 변경도 수행하지 않습니다.

## 운영 권장 순서

1. 테스트 Title에서 조회가 되는지 확인합니다.
2. `PLAYFAB_PLAYER_DATA_TEST_ENABLED=true`로 테스트 쓰기만 활성화합니다.
3. 테스트 계정의 `AutoSaveData` 또는 별도 테스트 세이브를 편집해 게임 반영을 확인합니다.
4. 감사 로그에 원문 없이 담당자와 변경 정보가 남는지 확인합니다.
5. 백업·복구 절차를 마련한 다음 필요한 경우에만 라이브 쓰기를 활성화합니다.
