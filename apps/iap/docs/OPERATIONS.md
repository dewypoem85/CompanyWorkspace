# 운영 안내

## 연결과 배포

1. 회사 포털에 `iap` 시스템과 `iap.access`, `iap.publish` 권한을 배포합니다. 포털 변경은 `company-org/company-portal` 저장소에 있습니다. `/api/internal/workspace/session?include=projects` 프로젝트 목록 응답을 함께 배포하고 웹에서 실제 포털 프로젝트를 연결합니다. `iap.publish` 부여 시 접근 권한도 함께 정규화됩니다.
2. 별도 서버 비밀 디렉터리에 `iap-connectors.json`과 키 파일을 만듭니다. [예시](../config/connectors.example.json)의 테스트 식별자를 실제 **테스트 앱** 정보로 바꾸고 사용하지 않는 연결은 제거합니다. 키 원문을 브라우저나 Git에 입력하지 않습니다.
3. 기본 운영은 시트 서비스 계정에 대상 시트 **뷰어** 권한만 부여하고 `sheets.writesEnabled: false`를 유지합니다. 웹에서 새 상품 원본 행을 만들 프로젝트만 서비스 계정을 **편집자**로 공유하고, 해당 서버 연결 프로필의 `sheets.writesEnabled`를 `true`로 바꿉니다. 이때 서버는 `spreadsheets` OAuth scope를 사용합니다. 스토어 쓰기 허용과 시트 쓰기 허용은 서로 독립입니다.
4. Compose 환경에 `IAP_DB_PASSWORD`, `COMPANY_SSO_SHARED_SECRET`, `IAP_ORIGIN`, 필요 시 `IAP_SECRETS_DIR`를 지정합니다. DB 비밀번호는 URL 안전 문자열을 사용하거나 `DATABASE_URL`을 적절히 인코딩합니다. 공유 SSO 비밀은 포털과 같아야 하며 32자 이상입니다.
5. 기존 `company-services` Docker 네트워크에서 포털 호스트명 `company-portal`에 접근 가능해야 합니다. HTTPS reverse proxy를 `product-upload:4180`으로 연결하고 포털 `Systems__Iap__BaseUrl`과 실제 origin을 일치시킵니다. 기본 도메인은 `https://iap.example.com`이며 DNS/프록시 설정은 별도입니다.
6. 저장소 루트에서 `powershell -ExecutionPolicy Bypass -File scripts/deploy.ps1`로 빌드·기동·상태 검사를 수행합니다. 이미 빌드한 이미지는 `-SkipBuild`로 기동합니다. 스크립트는 체크아웃을 초기화하거나 DB 볼륨을 삭제하지 않습니다. 시크릿 마운트는 읽기 전용으로 유지하고 컨테이너의 node 사용자가 읽을 수 있어야 합니다. SSO의 `/auth/sso/callback` form POST를 프록시가 막지 않도록 합니다.

`/workspace/iap`은 **회사 포털 진입 경로**입니다. 제품 서비스는 별도 origin의 `/`에서 구동합니다. HTML만 subpath 프록시로 옮기면 절대 `/api` 경로가 달라지므로 지원하지 않습니다.

### 회사 터널과 배포 확인

기존 Cloudflare 회사 터널 설정의 마지막 404 규칙 앞에 [IAP ingress 항목](deploy/company-tunnel-ingress.yml)을 추가합니다. 다른 서비스의 규칙은 보존합니다. `iap.example.com` DNS를 같은 터널로 연결한 뒤 ingress 검증을 통과한 설정을 적용합니다. 포털과 IAP는 동일한 `company-services` 네트워크를 사용합니다.

운영 컨테이너에서 다음 읽기 점검을 실행합니다. 지정 시트 ID를 전달하면 서버 서비스 계정의 읽기 권한과 표준 헤더도 확인합니다. 출력에는 시트 내용과 인증 정보가 포함되지 않습니다.

```powershell
Get-Content -Raw scripts/check-deployment.mjs | docker compose exec -T product-upload node --input-type=module
# 선택: 동일 명령의 exec -T 뒤에 -e IAP_TEST_SPREADSHEET_ID=<대상 ID> 추가
```

이 점검은 HTTPS/DB health, 비로그인 조회·변경 차단, 포털 로그인 리다이렉트, 서명 없는 내부 포털 요청 차단을 확인합니다. 인증 후에는 권한 있는 실제 계정으로 회사 포털의 **상품 관리**에 진입해 프로젝트 연결과 화면을 별도로 확인해야 합니다. 이 검사는 실제 스토어 쓰기 검증을 대체하지 않습니다.

처음 배포한 DB에는 테스트 상품이나 가짜 회사 프로젝트를 넣지 않습니다. 포털에서 제공한 프로젝트를 연결하고 `Products` 탭에 상품을 작성한 뒤 가져옵니다. 비어 있는 시트를 가져오면 `EMPTY_CATALOG`로 중단하며 기존 카탈로그를 지우지 않습니다.

### 웹에서 새 상품 원본 추가

상품 목록의 **새 상품 추가**는 `Products!A:E`에 `productKey,name,googleId,appleId,steamId` 순서로 새 행만 추가합니다. 저장 전 화면에 프로젝트·시트·추가 행을 표시하며, 성공 후 독립 상품 상세 페이지로 이동합니다. 기존 행 수정·삭제·ID 교체 기능은 없습니다.

운영 프로젝트의 시트 쓰기를 켜기 전에 별도 테스트 스프레드시트에서 다음을 확인합니다.

- 헤더가 정확하지 않거나 `writesEnabled`가 꺼져 있으면 시트와 DB가 모두 그대로 유지되는지 확인합니다.
- 동일 상품 키와 각 스토어 ID의 중복이 차단되는지 확인합니다.
- 행 추가 응답이 유실된 뒤 같은 요청을 보내면 완전히 같은 행만 성공으로 복구하고, 같은 키의 다른 값은 충돌로 멈추는지 확인합니다.
- 행 추가 이후 스냅샷 저장이 실패해도 성공한 시트 행을 삭제하거나 덮어쓰지 않는지 확인합니다.
- 신규 원본 추가 과정에서 Google Play·App Store·Steam 쓰기 요청이 한 건도 발생하지 않는지 확인합니다.

상품 상세는 **개요 → 상품 내용 → 가격 → 스토어 설정 → 등록 검토** 순서로 사용합니다. 스토어 가져오기는 별도 페이지에서 세 플랫폼을 읽고 웹 스냅샷에만 저장합니다. 등록 검토는 불변 계획을 만든 뒤 계획 ID URL로 이동하며 새로고침해도 같은 계획을 다시 표시합니다. Google·Apple 기존 상품은 계획과 실행에서 계속 외부 쓰기 없이 보호합니다.

배포 전에 회사 포털 DB는 SQLite backup API로 일관된 사본을 만들고 Data Protection 키, 기존 터널 설정, 이전 이미지 태그를 별도 비공개 경로에 보관합니다. IAP 업데이트 전에는 PostgreSQL 백업과 이전 IAP 이미지도 보관합니다. 롤백은 호환되는 이전 이미지를 재기동하고 필요한 터널 설정만 되돌립니다. DB 볼륨을 삭제하거나 DB 파일을 실행 중 덮어쓰지 않습니다. 스키마 변경이 있으면 해당 버전의 데이터 복구 절차를 먼저 확인합니다.

## 모바일 쓰기 활성화 조건

`writesEnabled: false`인 상태에서도 기존 상품 조회·차이 비교가 가능합니다. 신규 계획과 예외 계획의 실행 가능한 단계는 쓰기 검증을 통과해야 만들어집니다. 운영 계정에서 검증 기록을 임의로 채우지 않습니다.

테스트 계정에서 아래 항목을 검증하고 연결의 `verification`에 `testApp`, UTC `testedAt`, 보고서 경로/해시를 포함한 `evidence`, `duplicateCreateRejected: true`, `lostResponseStops: true`를 기록한 다음 `writesEnabled`를 켭니다. 이 값은 **담당자가 검증한 증거의 참조**이며 서버가 외부 테스트 수행을 자동 증명하는 서명은 아닙니다. 운영 서버 설정 권한을 제한해야 합니다.

- 비활성/초안/심사중/판매중 기존 테스트 상품을 일반 업로드해 외부 쓰기 요청 0건 확인.
- 시트 변경·Apple 가격 재선택 후 같은 테스트, 워커 재시작 후 같은 테스트.
- 대상 앱에서 생성 전용 API가 지원되는지 확인하고 중복 ID 생성이 거부되는지 검증.
- 동시에 같은 ID를 만드는 충돌을 재현하고 기존 값이 동일한지 읽기 비교.
- 프록시/테스트 하네스에서 생성 응답을 유실시키고 자동 재생성·인계가 없는지 확인.
- 예외 승인에 대해 ID/사용자/필드/값 변조, 재사용, 대기 중 10분 만료, 원격 변경 거부.

Google `legacySaleCountries`는 테스트에서 확인한 앱의 실제 구형 상품 판매 국가 목록입니다. 상품 화면에는 이 앱 범위를 읽기 전용으로 보여주며, 저장된 기존 `KR` 초안은 등록 계획에서 앱 범위로 대체합니다. 구형 API는 상품별 판매 국가 제한 기능을 제공하지 않아 `availability` 예외 변경은 지원하지 않습니다. 이 목록을 웹 요청에 맞춰 임의로 수정하면 안 됩니다. 호환성/판매 범위를 확인할 수 없거나 새 모델로 전환된 앱은 자동 쓰기를 끈 채 콘솔에서 처리합니다. Apple IAP 판매 지역은 앱의 판매 지역과 별도이므로 상품별 설정을 유지합니다. Apple 지역 목록은 App Store Connect에서 가져오고, 필요하면 `제공 지역 전체 선택`을 눌러 한 번에 선택합니다. `onetimeproducts.patch`를 신규 생성 대체 경로로 사용하지 않습니다.

가격은 배포 이미지의 `resources/pricing-matrix.csv`를 원본으로 사용합니다. 사용자는 상품 상세에서 KOR 소비자가격을 검색해 바로 선택합니다. 같은 행에서 Google의 같은 국가·통화 가격과 Steam의 통화별 지정 대표 국가 가격 및 내부 감사 스냅샷을 서버가 자동 생성합니다. 별도 가격표, 프리셋 생성·이름 입력·확정 단계는 없습니다. 빈 가격과 0원, 대응되지 않는 지역은 제외하며 임의 환산하지 않습니다. 가격 파일을 갱신할 때는 원본 CSV를 교체하고 전체 검증·이미지 재빌드·배포를 수행하며, 가격 데이터 버전 화면에서 전체 파일 해시를 확인합니다. 신규 Apple 상품에는 대상 상품의 KOR 가격 포인트를 다시 조회해 정확히 같은 판매가가 한 개일 때만 대한민국 기준 가격 하나를 반영합니다. 다른 상품의 가격 포인트 ID를 복사하거나 국가별 수동 가격을 만들지 않습니다. 판매 지역은 Apple territories API의 현재 목록에서 별도로 선택합니다. 심사 이미지는 상품 상세에서 PNG/JPG 파일을 선택하면 전용 `product-upload_iap-review-assets` 볼륨에 저장되고, 생성 계획에는 서버가 발급한 파일 ID만 기록됩니다. 이 볼륨과 PostgreSQL의 `review_asset` 메타데이터를 같은 시점에 백업해야 하며 한쪽만 복구하면 이미지 업로드 계획은 중단됩니다. 연결 설정의 기존 `reviewImages` 파일 참조도 호환됩니다. 동일 유형 최초 IAP 심사는 새 앱 버전과 함께 수동 제출해야 하므로 `APP_VERSION_REQUIRED`로 멈춥니다. API가 아직 지원되지 않는 계정이나 409 응답도 수정 대체 동작 없이 중단합니다.

## 작업 상태와 복구

| 상태 | 의미 / 처리 |
|---|---|
| `skipped` | 기존 모바일 상품. 모든 외부 쓰기를 생략 |
| `queued` | 미전송 또는 명확히 거절된 단계 대기. 지수 지연 후 같은 작업 재시도 |
| `running` | 현재 작업. 성공 증거와 각 단계 결과를 DB에 기록 |
| `done` | 계획된 단계 완료. Apple 심사 승인/실제 판매 개시와는 별개 |
| `needs_action` | 원격 변경, 권한/가격/API 제약, 미확정 요청. 자동으로 반복하지 않음 |

`needs_action` 작업은 읽기 전용 상태 조회로 조사합니다. DB의 `inflight`나 생성 성공 영수증을 수동 조작해 재시도하지 않습니다. 생성 응답이 유실됐다면 스토어에 실제로 존재하더라도 그 상품은 이후 **기존 상품**으로 취급하고 새 일회성 승인 계획으로 필요한 변경만 검토합니다. 안전하게 이미 완료한 단계를 제외할 수 있는 자동 증거가 없으면 작업을 중단하는 것이 정상 동작입니다.

승인은 한 작업에 소비됩니다. 같은 execute 요청을 재전송하면 같은 작업 ID를 반환합니다. 다른 작업이나 사용자에게 이전할 수 없습니다. 재시작 후에도 최초 계획과 연결 fingerprint를 검증하고 원본 밖의 단계/가격으로 바꾸지 않습니다. 연결 설정이 바뀌면 재개하지 않습니다. 작업 시작 후 이미 완료한 단계는 자동 원복하지 않습니다.

게임·스토어별 DB advisory lock이 서비스 워커들을 직렬화합니다. 외부 콘솔이나 다른 시스템에는 이 잠금이 적용되지 않습니다. 원격값은 실행 직전에 다시 비교하지만 Google/Apple/PlayFab이 조건부 쓰기를 지원하지 않는 호출의 마지막 조회와 쓰기 사이 외부 변경까지 원자적으로 막지는 못합니다. 예외 변경과 Steam 갱신 중 해당 스토어 콘솔의 동시 편집을 피합니다.

상품 목록 진입 시 세 플랫폼의 등록 상태를 읽기 전용으로 확인합니다. `상태 확인 필요` 상품은 미등록으로 간주하지 않으며 새로고침 후에도 실패하면 연결 권한을 점검합니다. App Store 현재 가격은 `App Store 현재 가격 전체 읽기`로 순차 조회하며, 실패한 상품은 행의 오류를 확인한 뒤 개별 재시도합니다. 상품 설정의 `App Store 전체 가격 읽기 (확장 가격 포함)`은 그 상품에 Apple이 허용한 가격 포인트를 직접 읽습니다. 확장 가격이 나오지 않으면 App Store Connect 계정의 추가 고가 가격 포인트 권한을 먼저 확인합니다. 숨김과 다시 표시는 웹 목록 설정만 변경합니다. 신규 업로드 대상 플랫폼은 Google Play·App Store·Steam이 기본 선택되며, 의도적으로 제외할 플랫폼만 사용자가 해제합니다.

## 백업·관측

PostgreSQL 전체 백업과 `product-upload_iap-review-assets` 볼륨을 정기 보관합니다. `entities` 테이블의 snapshot/plan/preset/audit/backup/sso_nonce/apple_prices/apple_equalizations/apple_territories/review_asset은 trigger로 수정·삭제를 막습니다. Steam의 전체 원문 백업은 작업 전에 DB에 남습니다. 운영 쓰기를 멈출 때는 연결의 쓰기를 비활성화하고 서비스를 재시작합니다.

`GET /api/health`는 DB 접근까지 확인합니다. 작업 이력은 웹에서, 감사 이력은 인증된 `GET /api/audit`에서 확인합니다. 서버 로그는 작업 ID와 오류 코드만 기록하며 외부 응답 원문/키를 출력하지 않습니다. API 응답에서도 세션 ID와 Apple 서명 업로드 URL을 제거합니다. 데이터 보존/백업 삭제 정책은 별도 승인된 운영 절차로 수행합니다.

SSO 세션은 포털에서 매 API 요청마다 다시 확인하고 외부 쓰기 직전 `iap.publish`도 재확인합니다. 포털이나 DB가 불가하면 작업을 진행하지 않습니다. 여러 워커를 띄울 때에는 DB connection pool 여유를 확보합니다. 기본 pool은 12개입니다.
