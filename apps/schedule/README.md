# 팀 일정

주간·월간·칸반 보기를 제공하며 직원별·프로젝트별·부서별·내 일정으로 전환합니다. 월간 달력은 기간 업무를 날짜마다 복제하지 않고 주 단위의 연속 리본으로 표시하며 프로젝트, 담당자와 상태를 리본에서 바로 확인할 수 있습니다. 업무에는 직원이 직접 만들고 종료할 수 있는 목표 그룹을 연결할 수 있고, 업무 상세에는 상세 일정과 등록자·완료자·완료 시각이 남는 공용 TODO를 함께 관리합니다. 상세 일정은 일반 보드에는 노출하지 않고 업무 상세와 내 일정에서만 표시합니다. 버전 내역은 프로젝트를 볼 수 있는 모든 직원이 수정할 수 있으며 모든 수정본과 작업자는 감사 이력에 남습니다. 세부 경계는 [목표·상세 일정·공용 TODO 계약](../../packages/contracts/schedule-work-planning.md)을 따릅니다.

버전 기록의 닫기 버튼·Escape·메뉴 이동·뒤로/앞으로 이동은 공통 초안 확인창을 거칩니다. 확인하는 동안 URL과 편집 내용을 유지하고 입력/저장을 잠그며, 취소하면 원문과 기존 history 위치를 보존합니다. 승인 직전 계정·전체 초안·기록 기준값을 다시 확인하며, 이 확인을 저장 진행으로 표시하지 않습니다. 다른 편집기의 동기 확인은 별도 전환 대상입니다.

업무/버전 편집창·이미지 확대창·날짜 선택/이동창은 회사 공통 팝업을 사용합니다. 계정 재확인 시 업무·버전 초안은 유지하고 날짜/이미지 창은 닫습니다. Escape로 자식 창만 닫으며 이미지 버튼 또는 날짜 입력으로 포커스를 돌려줍니다. 전송 중 닫기와 미저장 초안 확인은 유지합니다. DOM·테마·강제 종료/포커스 정책 및 남은 범위는 [공통 팝업 계약](../../packages/contracts/owned-modals.md)을 참고합니다.

업무 생성·수정·상태 변경은 공통 저장 도구와 확인창을 사용합니다. TaskPanel뿐 아니라 칸반의 상태 드롭다운과 드래그도 현재 계정·업무 상세·화면 행의 버전을 다시 확인하고, 전체 저장 응답을 검증한 뒤에만 보드 행을 이동합니다. 확인 취소와 처리 중에는 원래 열을 유지하고 컨트롤을 잠급니다. 입력 오류는 교정하고 충돌은 최신 내용을 비교하며, 미확정 결과는 같은 문서에서 편집기를 다시 열어도 반복 저장하지 못하도록 합니다. 저장 후 조회만 실패하면 `저장 결과 다시 조회`로 읽기만 재시도합니다. 업무는 [업무 저장 계약](../../packages/contracts/schedule-task-writes.md), 댓글은 별도 [댓글 저장 계약](../../packages/contracts/schedule-comment-writes.md)을 따릅니다.

업무 상세의 초기/자동 조회·업무/댓글 비교·보관/복원/댓글 삭제 전후 조회는 공통 읽기 도구를 사용합니다. 실패 시 마지막 정상 내용과 초안을 유지하고 `업무 다시 조회`를 제공합니다. 계정·권한 변경 시 자동 갱신과 쓰기를 잠그며 원래 계정의 명시적 재확인으로만 재개합니다. 보관·복원·댓글 삭제는 [업무 상세 작업 저장 계약](../../packages/contracts/schedule-task-actions.md)에 따라 현재 계정과 업무/댓글 기준 및 전체 저장 응답을 확인하고, 불확실한 요청을 같은 화면에서 반복하지 않습니다. 이미지 선택·붙여넣기·드롭은 계정 재확인과 파일 SHA-256·전체 첨부 응답을 검증하는 [이미지 업로드 계약](../../packages/contracts/schedule-image-uploads.md)을 사용합니다. 새 댓글·답글·수정은 최신 상세의 댓글 기준값과 전체 ACK를 확인하고 저장 뒤 목록 조회 실패 시 POST/PUT를 반복하지 않습니다.

업무·주요 일정 카드는 공통 카드 규칙으로 표시합니다. 프로젝트 색과 실선 테두리, 선택/비활성·두 테마의 강조를 공통으로 관리합니다. PC 날짜 셀 전체를 눌러 등록하는 동작과 키보드 등록, 업무 상세·칸반 드래그 ID를 검증합니다.

보드의 모두 펼치기/접기·크게 보기·기간 읽기와 행 펼침 버튼도 공통 규칙을 사용합니다. 색상 안내는 모바일에서도 열 수 있으며 겹친 업무의 배치와 직원·날짜별 업무 등록 동작을 유지합니다.

주간 일정·칸반 상단의 분류/필터/주 이동은 공통 컨트롤을 사용합니다. 주말 표시·선택한 주만과 상세 보기 설정도 같은 공통 checkbox의 18px 입력과 선택·포커스·비활성 상태를 사용합니다. 보기 설정은 공통 펼치기로 연결하며 날짜 미정·칸반·개인 TODO 왕복에도 필터와 보기 값을 보존합니다. 모바일 필터 폭·날짜 표시와 두 테마의 선택 상태를 검증합니다. 소유권과 남은 범위는 [탐색·필터 UI 계약](../../packages/contracts/schedule-board-controls.md)을 확인합니다.

예시 데이터와 오늘 문구도 공통 상태 pill의 warning/info 의미를 사용합니다. 모바일에서는 예시 표기를 숨기고 데스크톱 밀집 보드에서는 오늘 열 테두리를 유지하며, 앱별 라이트/다크 색상은 두지 않습니다.

개인 TODO의 완료 입력도 공통 checkbox를 사용해 18px 입력과 42px 터치 영역, 라이트·다크 선택 상태를 일관되게 표시합니다. 완료/되돌리기 API, 72시간 보관과 초안·충돌 보호는 기존 흐름을 유지하며 [기록·TODO 컨트롤 계약](../../packages/contracts/schedule-record-controls.md)을 따릅니다.

날짜 이동과 달력 내부의 연도·월·날짜도 공통 UI 규칙을 사용합니다. 선택/비활성과 주말·공휴일을 구분하며, 공휴일 조회 실패 시에도 날짜 선택은 유지하고 공통 재시도 안내를 제공합니다. 윤일·종료일 하한·중첩 달력 닫기와 모바일 연도 표시를 검증합니다.

일정 관리의 주요 일정 등록·수정·삭제와 보관함도 공통 입력·버튼·오류 안내를 사용합니다. 저장 전 현재 계정과 전체 생성 목록 또는 대상 행의 기준을 다시 확인하고, 공통 확인창과 전체 저장 응답을 통과한 뒤에만 초안과 목록을 갱신합니다. 긴 제목은 모바일에서 줄바꿈하며 선택 상태와 삭제/저장 버튼은 공통 테마를 따릅니다. 기존 주요 일정 권한·버전·초안과 상세 URL은 유지하며 저장 수명주기는 [주요 일정 저장 계약](../../packages/contracts/schedule-milestone-writes.md)을 따릅니다.

업무 편집과 본문·댓글·답글은 같은 공통 입력/버튼 규칙을 사용합니다. 날짜 입력과 달력 열기 버튼은 모바일에서 겹치지 않게 배치하고 본문 편집 높이도 보존합니다. 댓글 저장 수명주기는 공통 계약으로 전환했으며 공휴일 조회 등 별도 경계는 [업무·댓글 UI 계약](../../packages/contracts/schedule-task-controls.md)을 확인합니다.

버전 기록과 개인 TODO의 일반 입력·작업 버튼·버전 표는 회사 공통 UI를 사용합니다. 신규/기존 수정 라벨, 두 테마의 선택/비활성, 모바일 표/편집 폭을 함께 검증합니다. 저장·충돌·계정별 데이터 정책과 미전환 범위는 모노레포 [기록 UI 계약](../../packages/contracts/schedule-record-controls.md)에 정리되어 있습니다.

직원·프로젝트 선택창과 직원 멘션 검색은 공통 `CompanySearch`의 초성 검색을 사용합니다(셸 JS `20260909.1`). `ㄹㅈㅈ`, `라ㅈㅈ` 등의 입력을 지원하며, 권한으로 제한된 기존 목록 안에서만 검색합니다.

회사 포털의 직원 계정으로 사용하는 주간 일정표와 칸반입니다. 업무 하나가 독립된 게시글이며 날짜·상태가 바뀌어도 댓글·이미지·논의 기록이 유지됩니다.

Company Portal 공통 워크스페이스 바, 서비스 전환 메뉴, 모바일 내비게이션과 도메인 공용 테마를 사용합니다. 정식 진입 경로는 `https://company.example.com/workspace/schedule`이며 기존 `schedule.example.com`은 상세 링크와 호환을 위해 유지합니다. 일정 알림은 Schedule DB가 소유하고, 서명된 내부 읽기 API가 Portal 통합 알림센터에 사용자별 최신 알림만 제공합니다. 로컬 세션은 기본 7일이며 사용 중 슬라이딩 갱신됩니다.

## 개발

모노레포의 공통 페이지 계약과 React adapter를 사용합니다. 새 페이지는 루트에서 `npm run page:new -- schedule <slug> "제목"`으로 생성합니다. 사이드바·등록 경로·본문 연결 및 `server/WorkspaceRoutes.g.cs`는 생성 결과이며 직접 수정하지 않습니다. 자세한 규칙은 [공통 개발 문서](../../docs/DEVELOPMENT.md)를 확인합니다.

Node.js 22+, .NET SDK 10이 필요합니다.

```powershell
npm install
$env:ASPNETCORE_ENVIRONMENT='Development'
$env:DemoMode='true'
$env:DataPath='C:/dev/docker/schedule/data/demo'
dotnet run --project server --urls http://127.0.0.1:5180
```

다른 터미널에서 `npm run dev`를 실행하고 `http://127.0.0.1:4180/auth/demo`로 접속합니다. 시제품 로그인은 Development + DemoMode 명시 설정 + loopback 접속에서만 제공됩니다. 운영 환경에는 예시 데이터나 독립 로그인이 없습니다.

## 검증

테스트 도구는 보안 수정된 Vitest 4.1.11을 사용합니다. `npm ci --ignore-scripts` 뒤 `npm test`, `npm run build`로 검증합니다. 개발 의존성을 포함한 온라인 audit도 모노레포 CI의 필수 검사입니다. 버전 변경·공통 검사 규칙은 [공통 개발 문서](../../docs/DEVELOPMENT.md)를 따릅니다.

개인 TODO 삭제는 공통 확인창을 사용합니다. 추가·수정·완료·정렬은 서버 확인 응답을 검증하고 결과를 공통 상태 영역에 표시합니다. 성공 뒤 목록 장애는 읽기만 재시도하며 같은 변경 요청을 자동 반복하지 않습니다. 자동 갱신이 편집 기준 버전을 바꾸지 않으며, 충돌 시 초안을 유지한 채 최신 목록과 차이를 알립니다. 계정 ID 변경 시 이전 계정의 개인 목록/초안을 분리하고 서버의 본인 전용 접근 검증은 유지합니다.

업무 수정의 **변경 내용 비교**와 댓글 수정의 **댓글 변경 비교**는 같은 공통 비교창에서 수정 전·내 초안·현재 서버 값을 보여줍니다. 충돌한 필드는 사용할 값을 선택하며 비교 적용만으로 저장하지 않습니다. 적용 후 별도로 저장해야 하고, 검토 이후 다른 곳에서 다시 수정하면 기존 서버 버전 검사로 재충돌합니다. 권한 변경·조회 실패·조회 중 입력·비교 취소는 기존 초안을 유지합니다. 서버에서 제거된 첨부는 다시 업로드해야 하며 선택만으로 되살리지 않습니다.

댓글은 업무 편집 권한과 별개로 작성자만 수정할 수 있습니다. 삭제·보관된 댓글도 열린 초안은 유지하지만 저장할 수 없습니다. 신규/답글/수정의 저장 중 입력과 중복 전송을 막으며, 저장 성공 후 목록 조회만 실패했다면 저장과 조회를 구분하여 안내합니다. API 확인 응답이 불완전하면 초안을 지우지 않고 서버 상태 확인을 요구합니다. 다른 폼/확인창 및 전체 저장 수명주기 공통화는 후속 대상입니다.

```powershell
npm run build
dotnet build server/Schedule.csproj -c Release
```

구현·검증 현황 및 확정 범위: [IMPLEMENTATION.md](docs/IMPLEMENTATION.md).

## 사용

- 주간 일정의 토요일은 파랑, 일요일·등록 공휴일은 빨강으로 날짜와 열 배경을 구분합니다. 공휴일 이름을 함께 표시하며 오늘은 별도 테두리로 강조합니다. 모바일·다크 모드도 같은 의미의 색상을 사용합니다.
- 공휴일은 연차관리의 등록 정보를 부재 조회와 함께 읽습니다(`format=calendar-v2`). 임시·대체·회사 휴일도 연차관리 등록 기준이며 별도 달력 계산이나 데이터 복제는 없습니다. 조회 실패/구버전 연차 응답이면 공휴일 정보 미확인 안내를 표시하고 주말과 업무 조회는 유지합니다. 배포 순서: Leave → Schedule.

운영 주소: https://schedule.example.com — 회사 포털 계정으로 로그인합니다.

- 주간 일정에서 사람별 업무 기간과 부재를 함께 확인하고, 칸반에서 같은 업무의 상태를 옮깁니다.
- 조회 기간은 1주·2주·4주를 선택합니다. 기본 요약 보기에서 겹친 업무는 직원 옆 `+N개`로 펼치고, 카드 정보가 필요하면 자세히 보기로 전환합니다.
- 업무를 열면 본문, 이미지, 댓글과 답글, 멘션 및 변경 이력을 확인할 수 있습니다.
- 주요 일정을 누르면 상세 내용을 읽을 수 있습니다. 제목·프로젝트·최대 10,000자의 상세 내용을 공유하는 게시글에 타입과 마감일을 여러 개 추가할 수 있으며, 각 마감일에는 최대 200자의 선택 메모를 둘 수 있습니다. 주간·월간 일정표는 메모가 있으면 해당 메모를 표시하고, 비어 있으면 주요 일정 제목을 표시합니다.
- 부서/프로젝트/담당자 필터, 내 일정, 날짜 미정 목록을 제공합니다.

## 통합 워크스페이스 UI (2026-09-07)

- 직원 행·모바일 목록·댓글·멘션은 공통 `Avatar` 컴포넌트로 Portal 프로필 사진을 표시합니다. `company-context` 갱신 이벤트를 구독하므로 사진 교체/삭제와 로그아웃도 반영됩니다. 사진이 없는 경우에만 이름 첫 글자로 대체합니다.
- 주간 일정은 필터 적용 후 로그인한 직원의 행을 맨 위에 표시합니다. 나머지 직원 순서는 유지하며, 필터에 포함되지 않는 본인 행을 강제로 추가하지 않습니다.

- 상단바는 Company Portal의 `/js/company-workspace.js`, `/css/company-workspace.css`를 공통 사용합니다. 로고의 홈 이동, 종 모양 알림, 개인 설정/로그아웃, 권한별 서비스 전환, 테마를 한 곳에서 제공합니다.
- 서비스 내부 메뉴는 `.cw-sidebar`에만 배치합니다. 각 서비스에 별도 계정·알림·테마·회사 홈 버튼을 추가하지 않습니다. 900px 이하에서는 상단 메뉴 버튼으로 하위 메뉴를 엽니다.
- 테마는 의미별 `--cw-*` 토큰을 사용합니다. 선택/미선택 상태는 `aria-current` 또는 `aria-pressed`와 함께 표현하며 색 반전 필터를 사용하지 않습니다.
- `/api/workspace/context`가 실제 계정과 허용된 서비스만 반환합니다. 관리자 계정은 모든 서비스를, 공용 계정은 부여받은 서비스만 볼 수 있습니다. 화면 숨김과 별개로 각 서비스 백엔드도 권한을 검증합니다.
- 개인 설정 `/settings/profile`: 사진만 변경 가능합니다. 브라우저에서 가운데를 256×256 PNG로 변환하고 서버에서 크기/CRC/압축 해제 크기를 검증합니다. 이름·부서·역할 수정 API는 제공하지 않습니다.
- SSO 토큰과 서비스 세션에 `sid`가 포함됩니다. 서비스는 HMAC 서명된 60초 토큰(`aud=workspace-session`)으로 Portal의 `/api/internal/workspace/session`에서 세션과 최신 권한을 확인합니다. 로그아웃은 현재 브라우저의 sid를 폐기하므로 모든 하위 서비스의 기존 세션이 거부되며 다른 기기의 세션은 유지됩니다.
- 내부 인증 연결 실패는 503으로 실패 처리하며 인증을 우회하지 않습니다. Node 서비스의 내부 주소는 `COMPANY_PORTAL_INTERNAL_URL`(기본 `http://company-portal:8080`), Leave는 `CompanyPortal:InternalUrl`, Schedule은 `Portal:InternalUrl`입니다. Docker `company-services` 네트워크와 서비스 간 동일 SSO 키가 필요합니다.
- 알림 원본 DB는 각 서비스에 남습니다. 내부 GET `/api/internal/company-notifications?format=workspace-v2`는 `{items,unreadCount}`, 형식 미지정은 기존 배열을 반환합니다. 내부 POST `.../read?id=ID` / `.../read`는 서명 토큰의 사용자 소유 알림만 읽음 처리합니다. Portal은 권한 있는 출처만 조회하며 일부 실패를 UI에 표시합니다.
- Portal의 쓰기 API는 인증 쿠키와 `X-Workspace-CSRF`를 함께 검증하고 허용된 서비스 origin에만 CORS를 제공합니다. 각 서비스 CSP의 `connect-src`, `img-src`는 `https://company.example.com`을 허용합니다.
- 배포 시 Portal DB와 DataProtection 키를 백업하고 Portal 및 모든 하위 서비스를 함께 갱신합니다. 새 `WorkspaceSessions`/`WorkspaceProfiles` 테이블은 추가 방식이며 기존 직원·업무 데이터를 이동/삭제하지 않습니다. 구버전 서비스 세션은 최초 접근 시 한 번 SSO 재연결이 필요할 수 있습니다.

## 버전 기록 편집·충돌 검토

- `useReleaseEditor`가 공통 상태·3방향 비교·history/navigation 이탈 보호를 사용합니다. 저장 전 현재 기록과 권한을 다시 확인하고, 다른 사람이 수정했다면 초안을 유지한 채 `버전 변경 비교`로 검토합니다. 비교 적용만으로 저장하지 않습니다.
- 기본 버전과 마이너 기록은 같은 편집창에서 수정·삭제할 수 있습니다. 기본 버전에 마이너가 남아 있거나 다른 기록의 복귀·해결 대상으로 연결된 기록은 연결을 먼저 정리해야 삭제됩니다. 삭제 전 대상과 Version을 다시 확인하며 취소하거나 실패하면 기록을 유지합니다.
- `releaseReview`가 날짜/미기재 여부, 롤백·해결 마이너 조합과 저장 응답의 ID·버전·원문을 확인합니다. 서버의 버전 충돌/프로젝트 인가/관리자·책임자 정책과 감사 기록은 그대로입니다. 보관 프로젝트의 기존 기록도 수정할 수 있습니다.
- 전송 중 입력·중복 제출을 잠그며 확인된 저장과 후속 목록 오류를 분리합니다. `목록 다시 확인`은 저장을 반복하지 않습니다. 신규 등록의 불완전/통신 오류는 등록 여부를 확정할 수 없으므로 목록을 확인한 뒤 다시 여세요. 계정 변경/페이지 해제 후 늦은 응답과 저장 이전의 이력 응답은 적용하지 않습니다.
- 기본/마이너/미기재 목록의 로딩·오류·권한 없음·빈 결과도 공통 상태를 사용합니다. 목록이 잘못됐거나 다른 프로젝트의 응답이면 표시하지 않고 재조회를 제공합니다. 일시적인 새로고침 장애에는 확인된 행을 유지하지만 계정 변경/401/403에는 이전 행을 지웁니다. 마이너·미기재·변경 이력 펼치기는 공통 컨트롤러가 표시·ARIA·포커스를 관리하며 작은 화면에서는 펼친 내용이 표 전체 너비를 따라 늘어나지 않습니다.
- 버전 상태는 공통 상태 pill을 사용합니다. 안정·해결 완료는 success, 불안정·롤백·건너뜀은 danger, 상태 미기재는 neutral이며 별도 크기·색·다크 팔레트를 복제하지 않습니다.
- 검증: 모노레포에서 `npm --prefix apps/schedule test`, `npm --prefix apps/schedule run build`, `dotnet test apps/schedule/tests`, 루트 브라우저 `--grep "release editor|release lists"`. 다른 일정 폼 전환은 별도로 남습니다.

주간 일정은 좌우 스크롤로 주를 추가 조회하며, 화면 표시 1·2·4주와 요약 행 높이를 조절할 수 있습니다. 주요 일정은 일반·검수·업데이트 타입을 지원합니다. 새 업무는 최초 담당자가 참여 중인 활성 프로젝트 가운데 번호가 가장 빠른 항목을 기본 선택하며, 미지정이나 다른 프로젝트로 바꿀 수 있습니다. 동료 업무를 등록하면 담당자에게 알림이 전달되며, 기존 수정 권한은 유지됩니다.

업무는 시작일과 종료일 한 쌍으로 표시합니다. 버전 기록 메뉴는 프로젝트별 기본 버전과 마이너(770, 770.1 등), 최종 버전, 최초 업데이트, 패치 및 문제 해결 이력을 관리합니다. 기존 시트 데이터는 자동으로 가져오지 않습니다.

## 공통 초기 정보·일정 조회

초기 정보와 주간/칸반/날짜 미정 목록은 `useScheduleData`와 공통 읽기 관찰 세션을 사용한다. 일시 오류에는 같은 조건의 정상 목록을 유지하고, 조건 변경에는 이전 결과를 숨긴다. 계정/권한 변경에는 보드를 비우고 문서를 다시 열도록 안내한다. 이미 열린 초안과 같은 계정의 명시적 변경 비교는 보존하지만 이전 계정 정보로 새 편집기를 만들지 않는다.

`scheduleReads`의 전체 응답/연속 페이지 검증과 `packages/contracts/schedule-reads.md`를 따른다. 30초 관찰 제한은 서버 조회/쓰기 롤백이 아니다. 읽기 재시도는 GET만 수행하며 실패 안내를 폴링으로 지우지 않는다. 업무·댓글·이미지 업로드·주요 일정 저장은 각각의 독립 계약에 연결했으며 다른 쓰기는 별도 범위다.
